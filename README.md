# Uplink cutover over NETCONF (SR Linux + Ansible)

Moves a dual-homed site's two fiber uplinks to new ports one at a time, with continuous traffic running.
The change uses the NETCONF candidate datastore, `<validate>`, a confirmed commit with automatic rollback,
and an IS-IS metric drain. Measured results are in [FINDINGS.md](FINDINGS.md); raw output is in `results/`.

- **NOS:** Nokia SR Linux **26.7.2-519** (`ghcr.io/nokia/srlinux:26.7.2`, node type `ixr-d2l`). I used the image
  already on the server, because the server disk was 99% full and couldn't take a fresh pull.
- **Ansible:** ansible-core 2.19.15 with ansible.netcommon 8.7.1, plus ncclient, all in a venv on the lab server.
- **Containerlab:** 0.78.2 on the lab server (<lab-server>).

The spare ports are cabled and admin-up, but have no subinterface until the cut. **Precondition: the new port must
already be lit and admin-up.** The playbook deliberately never changes port admin-state, so it can't undo a
shutdown someone made on purpose. Loopbacks are
csr1 10.0.0.1, agg-01 10.0.0.11 and agg-02 10.0.0.12. The aggs redistribute a static /32 to h2, so csr1
reaches h2 over two equal-cost paths.

NETCONF runs on port 830 in the mgmt network-instance (`system ssh-server mgmt-netconf` +
`system netconf-server mgmt`). The Ansible user is `ansible` / `Ansible123!` with role `netconf-ops`. That role
is limited to get, get-config, get-schema, edit-config, lock, unlock, validate, commit, cancel-commit,
discard-changes and close-session (no copy-config, delete-config or kill-session).

## Reproduce

Everything runs on the lab server. From the Mac (if `ssh` hangs at public-key auth, the macOS SSH agent is stuck:
add `-o IdentityAgent=none`, e.g. `rsync -e "ssh -o IdentityAgent=none" ...`):

```bash
rsync -a --exclude 'clab-*' ~/code/Nokia_Lab/cutover/ <lab-server>:nokia_lab/cutover/
ssh <lab-server>
cd ~/nokia_lab/cutover
```

On the server:

```bash
# 1. lab
docker tag ghcr.io/nokia/srlinux:latest ghcr.io/nokia/srlinux:26.7.2   # or: docker pull ghcr.io/nokia/srlinux:26.7.2
containerlab deploy -t cutover.clab.yml

# 2. tooling (one time)
python3 -m venv ~/nokia_lab/cutover-venv
~/nokia_lab/cutover-venv/bin/pip install 'ansible-core>=2.17,<2.20' ncclient
source ~/nokia_lab/cutover-venv/bin/activate
(cd ansible && ansible-galaxy collection install -r requirements.yml -p ./collections)

# 3. NETCONF hello: candidate, confirmed-commit:1.1, validate:1.1
python bin/nc_hello.py

# 4. the change, one uplink at a time. Dry run by default: lock, edit candidate, validate, diff, discard, unlock.
cd ansible
ansible-playbook uplink_cutover.yml -e link=a -e phase=drain
ansible-playbook uplink_cutover.yml -e link=a -e phase=drain   -e apply_change=true
ansible-playbook uplink_cutover.yml -e link=a -e phase=cut     -e apply_change=true
ansible-playbook uplink_cutover.yml -e link=a -e phase=restore -e apply_change=true
ansible-playbook uplink_cutover.yml -e link=b -e phase=drain   -e apply_change=true
ansible-playbook uplink_cutover.yml -e link=b -e phase=cut     -e apply_change=true
ansible-playbook uplink_cutover.yml -e link=b -e phase=restore -e apply_change=true
cd ..

# 5. the measured tests (each resets both links to the original ports first)
python bin/nc_semantics.py                                    # confirmed commit vs session close/drop/persist
python bin/cutover_test.py paths                              # which uplink each of the 8 flows uses
python bin/cutover_test.py full                               # A drain/cut/restore, then B, with traffic
python bin/cutover_test.py nodrain-1 drained-cut-1            # before/after comparison (repeat as you like)
python bin/cutover_test.py rescue-wrong-port rescue-far-end-shut
python bin/kill_test.py persist                               # kill playbook after commit (default playbook)
python bin/kill_test.py nopersist                             # same with -e persist_commit=false
python bin/cutover_test.py reset                              # back to original ports, normal metric

containerlab destroy -t cutover.clab.yml --cleanup
```

## What one run does

The playbook runs `hosts: link_<x>`, which is both ends of the link at once. It holds one NETCONF session per
node for the whole run (Ansible's persistent connection), and that session is what keeps the lock.

1. **Pre-check:** read IS-IS adjacencies on csr1. The *other* uplink must be up, on either its old or new port,
   or the run stops. For `cut`, the link must also already be drained (metric 1000) on both ends unless
   `-e skip_drain=true`.
2. **`<lock>`** the candidate. If the lock is refused because the candidate holds uncommitted changes, stop and
   explain. `-e discard_stale_candidate=true` discards them first. See FINDINGS for why this happens.
3. **`<edit-config>`** with target candidate only (`netconf_config target=candidate commit=false`). Running is
   never written directly.
4. **`<validate>`** with source candidate.
5. **Diff:** `<get-config>` of running and candidate for the touched subtrees, then print a unified diff.
6. **Dry run** (the default): `<discard-changes>`, `<unlock>`, stop.
7. **`<commit>`** with `<confirmed/>`, `<confirm-timeout>` (120 s) and `<persist>` (a per-run id).
8. **Verify:** wait up to 60 s for this link's IS-IS adjacency on the active port, then recheck the other uplink.
   Each node sets `checks_passed`, and a gate task fails on *both* nodes unless *every* node passed.
9. **Confirm:** `<commit>` with `<persist-id>`, then `<unlock>`.

**Rescue** (any failure after the lock): `<cancel-commit>` with persist-id if a commit is pending, then
`<discard-changes>` and `<unlock>`, then fail loudly with the failing task and reason.

| Phase | Port carrying the VLAN | IS-IS metric |
|---|---|---|
| drain | old | 1000 |
| cut | new (old subinterface removed) | 1000 |
| restore | new | 10 |
| baseline (lab reset) | old (new subinterface removed) | 10 |

## Operational notes (from the tests; details in FINDINGS.md)

- **Kill a run cleanly.** `kill -9` of `ansible-playbook` leaves its forked workers *and* the persistent NETCONF
  connection daemons (`ansible_connection_cli_stub.py`) running. The daemons idle out after
  `[persistent_connection] connect_timeout` (30 s).
- **Pending commit vs. session.** With the default `<persist>`, a pending commit doesn't depend on any of those
  processes: it rolls back when `confirm_timeout` expires. To roll back sooner from another session, use
  `<cancel-commit><persist-id>…</persist-id></cancel-commit>`. The id is printed in the `7. CONFIRMED-COMMIT-SENT`
  task.
- **Stale candidate after a rollback.** When a commit is rolled back after its session is gone, the next run stops
  at step 2 with "candidate has been modified". Check what is in the candidate, then rerun with
  `-e discard_stale_candidate=true`.
